# /sales-hearing — クライアントへのヒアリング → 分類と設定の構築

入力: `$ARGUMENTS`

質問は `sales/_templates/hearing.json`（33 問・6 章: 商材／営業先／リストの分け方／営業文／運用／共有と通知）。各質問の `maps` が反映先。
`T` = `node sales/scripts/targets.mjs`（既定以外のクライアントは `--client <slug>`）、`<C>` = `sales/clients/<slug>`。

## クライアントの決め方
`/sales-intake` と同じ。まだ登録が無ければ `T init <slug> --name "<社名>" --use` で作ってから始める（slug はローマ字、そう述べる）。

## どのモードで動くか
| 入力 | モード |
|------|--------|
| 「シートを作って」、または回答がまだ何も無い | **1. シート作成** |
| 「対話で」「今聞いて」、またはユーザーがその場で答えられる | **2. 対話** |
| Google ドキュメントの URL・記入済みの内容・議事録・音声の書き起こし・メールの貼り付け・ファイル | **3. 反映** |

---

## 1. シート作成（先方に送って記入してもらう）

1. 事前記入を作る: `<C>/offering.md` `icp.md` `config.json` が埋まっていればそこから、無ければ先方の公式サイトを WebFetch して、分かることだけを「現在の理解」として JSON にする（scratchpad）。**推測で価格・実績を書かない。** 分類（C 章）は空のままにする（先方に選んでもらう）。
   ```json
   {"A1": "株式会社○○ / https://…", "A2": [["商材名","一言","価格","含む","含まない","納期"]], "B1": [["業種","規模","地域","予算","特徴"]]}
   ```
2. `T hearing --prefill <json>` → `<C>/hearing/sheet.html` と `sheet.md`。
3. Google Drive コネクタがあれば（ToolSearch で `google drive`）、先に `google-workspace` スキルを読み、`create_file` で `textContent` = sheet.html、`contentMimeType` = `text/html`、`title` = 出力された推奨タイトル → Google ドキュメントに変換される。`<C>/config.json` に `"hearing": {"doc_id": "…", "doc_url": "…"}` を記録。
   - コネクタが無ければ sheet.md（または `docx` スキルで Word）を `SendUserFile` で渡す。
4. **先方への共有はしない**（共有・送信は外部への送付なので、ユーザーが明示的に頼んだ時だけ `share_file`。その時も宛先を確認してから）。
5. 報告: ドキュメントのリンク、事前記入した問の数、先方に特に答えてほしい問（A2 価格・A3 実績・C1〜C5 分類・D1 名義・D6 直接連絡・F1 共有先・F2 使う人）。

## 2. 対話（チャットで聞き取る）

- 章ごとに 2〜4 問ずつ聞く。選択式は選択肢を示す。答えが返るたびに `<C>/hearing/answers.json` に追記する。
- すでに分かっている問（offering.md 等から）は「○○で合っていますか」と確認だけにする。
- 「分からない」「後で」は空欄のまま進める。全部終わったら **3. 反映** へ。

## 3. 反映（回答 → 設定）

### 3-1. 回答を記録する
- Google ドキュメント: `read_file_content`（`hearing.doc_id`、または URL の id）。貼り付け・議事録・ファイルはそのまま読む。
- 選択式の問は ☑ ■ ● ○ ✓ ✔ などの印・太字・色付け・残っている選択肢（他を消した場合）を「選択」とみなす。どれが選ばれたか判断できない問は空欄にし、報告で確認を求める。
- 質問 id ごとに回答を抜き出し、`<C>/hearing/answers.json` に保存:
  ```json
  {"meta": {"date": "YYYY-MM-DD", "respondent": "氏名（役職）", "source": "Google ドキュメント / 打ち合わせメモ / チャット"},
   "answers": {"C1": "業種別", "C2": "製造／飲食／IT／その他", "C5": [["予算帯","〜50万／50〜200万／200万〜","エージェント"]]}}
  ```
  議事録など自由形式の場合は、該当する発言を要約して入れ、はっきりしないものは入れない（推測で埋めない）。
- `T hearing --answers <C>/hearing/answers.json` で `<C>/hearing/answers.md`（回答記録）を作る。

### 3-2. 分類を組み立てる（C 章 → `config.json` の `sheet`）
書き方の詳細は `sales/_shared/schema.md`「分類設定」。

| C1 の回答 | `sheet.tabs` の作り方 | あわせて設定するもの |
|-----------|----------------------|---------------------|
| 見つけた場所（標準） | 標準のまま（`tabs` を書かない）。C4 で標準以外のサイト（ココナラ等）があれば、そのサイトのタブを追加 | `platforms_extra` に C4 の追加サイト |
| 業種別 | C2 の区分ごとに `{"name": "製造", "match": {"業種": ["製造"]}}` | `industries` を C2 の区分と同じにする（最後に「その他」） |
| 提案する商材別 | 商材 id ごとに `{"name": "<商材名>", "match": {"推奨サービス": ["<id>"]}}` | `overlap: true` を推奨（1 社に複数の商材を提案するため） |
| 地域別 | 独自項目「エリア」（`values` = C2 の区分）を作り、区分ごとに `{"match": {"エリア": ["関東"]}}` | 所在地は自由記入なので、タブの条件は「エリア」にする |
| 優先度別 | `{"name": "A（最優先）", "match": {"ランク": ["A"]}}` を A/B/C で | `fallback_tab` を「未評価・除外」に |
| その他 | 回答の意図に最も近い列（標準の列か独自項目）を条件にする | 判断した理由を報告に書く |

- **タブは 1 つの軸で分ける。** 2 つ目以降の軸は列（独自項目や業種・推奨サービス）にして、スプレッドシートのフィルターで見る。タブは多くても 10 程度。
- C3 → `overlap`（すべてに表示 = true）。どれにも当てはまらない行は `fallback_tab`（既定「その他」）。
- C5 → `custom_columns`: `{"name": "予算帯", "values": ["〜50万", "50〜200万", "200万〜"], "editable": false}`。記入する人が先方・送付者なら `editable: true`（人が編集する列になり、取り込み対象になる）。選択肢が無ければ `values` を書かない。複数選べる項目は `multi: true`。
- C6 → `hide_columns`（必須列は隠せても入力は必要。企業特定の候補列を隠したい場合は理由を確認する）。
- C7 → `statuses`: 標準の並びに段階を挿入する（例: 送付済 → 返信あり → **アポ確定** → 商談中 → **見積提出** → 受注）。**未着手・調査中・提案作成済・送付済・除外は必ず残す**（エージェントが自動で使う）。
- D5 に「電話」等があり標準の接触チャネルに無い言い方なら `channels_extra`。

### 3-3. ほかの設定に反映する
| 章 | 反映先 |
|----|--------|
| A1〜A6 | `offering.md`（§0 出典に「ヒアリング YYYY-MM-DD」）・`config.json` の `services`（A2 の商材ごとに id を付ける）・`outreach.md` §2 署名 |
| B1〜B5 | `icp.md` §1〜2（`【仮説】` を回答で置き換える）。B4 の取引先は `icp.md` §1 除外に列挙 |
| D1〜D6 | `outreach.md` §1（名義・差出人・返信先）・§3 CTA・§5 チャネル・§6 NG。D6 は §5 に「直接連絡: 可 / 応募欄のみ / 要相談」として明記 |
| E1〜E3 | `outreach.md` §1（送付前の確認者）・運用メモ（目標件数・報告の頻度は `outreach.md` 末尾に「運用」として記録） |
| F1〜F6 | `config.json` の `share`（下の 3-3b） |

### 3-3b. 共有の方法を組み立てる（F 章 → `config.json` の `share`）
| 問 | 設定 |
|----|------|
| F1 共有する場所 | `platform`: Google スプレッドシート → `google_sheets`、Notion → `notion`、Excel → `excel`、kintone など → `csv`。「こだわらない」なら、編集する人が 2 人以上で 1 社ごとに提案文や調査を読み込むなら `notion`、それ以外は `google_sheets` を選び、理由を報告に書く |
| F2 使う人 | `members`: `[{"name": "佐藤", "role": "送付", "access": "edit", "email": "…"}]`（`access` は edit / comment / view） |
| F3 御社の見え方 | `client_access`: 見なくてよい → `none`、見るだけ → `view`、コメント → `comment`、編集 → `edit`。御社側で見る方は F2 の表から `client_contacts` に分ける |
| F4・F5 通知 | `notify.channel`: Slack → `slack`、Chatwork → `chatwork`、LINE WORKS → `line_works`、Teams → `teams`、メール → `email`、不要 → `none`（複数なら主に使うもの）。`notify.target` に F5 |
| F6 更新の頻度 | `update_timing`: 取り込むたび → `each_intake`、1 日 1 回 → `daily`、週 1 回 → `weekly`、依頼時 → `manual`。`notify.frequency` も同じにする |

- `T share` で検査する。注意（Excel で複数人が編集する、など）は内容を報告に含め、代わりの方法を 1 行で添える。
- 必要なコネクタ（Notion・Google Sheets・Slack）が未接続なら、`read_documentation`（topic `connectors.add`）でつなぎ方を確認してユーザーに伝える。
- メンバーや先方への招待は、ここでは行わない（ユーザーが頼んだ時に `/sales-list` で行う）。

既存の内容を書き換える時は、何をどう変えたかを報告に必ず書く。回答が無い項目は元の内容（`【要確認】` `【仮説】`）を残す。

### 3-4. 検証とプレビュー
1. `T config` で分類設定を検査する（エラーは直す。注意は内容を確認する）。
2. 既に営業先が登録されていれば `T validate` と `T migrate`（独自項目の追加・削除に合わせて CSV を変換。削除した項目の値は備考へ移る）。登録済みの行に独自項目の値を入れられる場合は `T apply` で埋める。
3. `T sheet --demo` で分類の確認用プレビュー（タブごとに例の行）を作り、共有先に合わせて見せる（Google スプレッドシート・Excel は xlsx、Notion は `T notion-schema` のプロパティとビューの一覧）。タイトルは `【分類プレビュー】…`。
4. 報告:
   - 分類の表（タブ名・入る行・列）。`T config` の出力をそのまま使う
   - 追加した独自項目・ステータス・プラットフォーム
   - 共有の方法（`T share` の出力）と、つなぐ必要のあるコネクタ
   - 各ファイルの変更点（1 行ずつ）
   - まだ埋まっていない重要な項目（価格・実績・名義・直接連絡の可否）
   - プレビューのリンク
   - 次の一手: 案件を `/sales-intake` で取り込む

## 原則
- ヒアリングの回答に無いことを、回答として書かない。
- 分類はあとから何度でも変えられる（`config.json` を直して `T migrate` → `/sales-list スプレッドシートを更新`）。迷ったら標準の分類で始め、運用しながら直すことを提案する。
- ヒアリングシートや回答を先方・第三者に送るのは、ユーザーが頼んだ時だけ。
