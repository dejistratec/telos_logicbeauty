# /sales-intake — 取り込み・企業特定・調査・登録

入力: `$ARGUMENTS`

## クライアントの決め方
- 引数に `--client <slug>` があればそれ。なければ `sales/clients/ACTIVE` の既定（`node sales/scripts/targets.mjs clients` で確認）。
- 既定が無く候補が複数ならユーザーに選んでもらう（止まってよいのはこの質問だけ）。1 つしかなければそれを使い、そう述べる。
- 以降 `<C>` = `sales/clients/<slug>`。スクリプトは `node sales/scripts/targets.mjs --client <slug> ...`（既定なら `--client` 省略可）。

## 先に読むもの（毎回）
1. `sales/README.md` の「守るべきルール」
2. `<C>/offering.md`（何を売るか）／ `<C>/config.json`（商材 id）
3. `<C>/icp.md`（誰を狙うか・配点）
4. `sales/_shared/schema.md`（列と許可値）／ `sales/_templates/research.md`

## 手順

### 1. 原文を保存する
- 入力がテキストなら、`sales/_templates/intake.md` の構成で `<C>/intake/<id>_<slug>.md` に**改変せず**保存する。
  - `id` は `node sales/scripts/targets.mjs next-id`。
  - ファイルの slug は英数字とハイフン（例: `apparel-d2c-tokyo`、`salon-nail-osaka`）。企業名が分かれば英字表記、分からなければ業種＋地域。
- 入力が URL なら WebFetch で本文を取得して同様に保存（取得できなければユーザーに貼り付けを依頼）。
- 入力が `<C>/intake/` のファイルパスなら、それを読む。
- 複数案件がまとめて貼られたら、1 件ずつ分けて以下を繰り返す。
- プラットフォームを判定する（「ランサーズ」「Lancers」「発注なび」「クラウドワークス」、URL のドメイン、文体から）。判定できなければ `その他`。

### 2. 手がかりを抽出する
固有名詞・ブランド名・商品名／業種／地域／数値（店舗数・従業員数・創業年・予算・フォロワー数）／URL の断片／独特の言い回し／希望する業務範囲・納期・予算／募集者の語彙と文体。

### 3. 企業を特定する（確度付き）
- WebSearch を 2〜5 回。「特徴的な語句の引用検索」「業種＋地域＋特徴」「商品名＋SNS」を組み合わせる。
- 候補のサイトを WebFetch で開き、**独立した一致点**を数える: 事業内容／所在地／規模／商品名／文言の一致／開設時期。
- 確度: **高**（一致点 3 以上、矛盾なし）／ **中**（2 つ、または 1 つが決定的）／ **低**（1 つ、候補が複数残る）／ **特定不能**（絞れない。`企業名` は `（特定不能）業種＋特徴`、匿名プロファイルとして進める）。
- 検討して外した候補と理由も残す。**確証がないものを断定しない。**

### 4. 公開情報を調査する（ログイン不要の範囲のみ）
- **クライアントの商材に関係する領域**を中心に見る（`offering.md` の「向いている相手」が観察できる場所）。例: SNS 運用の商材なら Instagram / LINE / 広告ライブラリ、Web 制作なら現行サイトの品質・導線・更新頻度、採用支援なら求人媒体・採用ページ、業務システムなら募集文の現行ツール名。
- 共通で見るもの: 公式サイト（商材・価格帯・ターゲット・トーン・問い合わせ手段・**営業 NG 表記の有無**）／ ニュース・採用・プレス（直近 6 か月の「変化」）／ SNS の有無と活用度（検索結果のスニペット範囲。ログインが必要な内容は取らない）。
- 取れなかった項目は「未確認」。推測は「推測:」を付ける。

### 5. 課題仮説・推奨サービス・切り口を決める
- 課題は**相手の言葉**（募集文・投稿の引用）で先に書き、その後にこちらの仮説。
- 推奨サービスは `offering.md` §2 の「向いている相手」「組み合わせの定番」から選ぶ（主→副、`config.json` の id で）。
- 提案の切り口を 3 つ。少なくとも 1 つは**冒頭フックに使える固有の観察**（具体的な投稿・商品・文言）。
- 文体の読み取り（敬体/常体・絵文字・英語・語彙・意思決定者が個人か会社か）を表にする。

### 6. ICP スコアを出す
`<C>/icp.md` §3 の配点どおりに内訳を書き、補正ルールを適用し、ランクを決める。除外条件に当たれば理由を明記して「除外」。

### 7. 調査メモを書く
`sales/_templates/research.md` の構成で `<C>/research/<id>_<slug>.md` を作成。frontmatter（クライアント slug 含む）を埋める。

### 8. リストに登録する
JSON を一時ファイル（scratchpad）に書き、`node sales/scripts/targets.mjs add <file>` で追加する。
- `接触チャネル`: プラットフォーム経由（発注なび／ランサーズ／クラウドワークス等）なら **`プラットフォーム応募`**。それ以外は営業 NG 表記がなければ `問い合わせフォーム` / `メール` / `Instagram DM` のうち相手に合うもの、無ければ `未定`。
- `ステータス` は `調査中`、`次アクション` は `提案文作成`、`期限` はランク A なら 2 日後、B なら 7 日後。
- `調査メモ` に research のパス（リポジトリルートから）、`備考` に `特定確度: 高/中/低/特定不能（根拠の要約）`。
- 重複エラーが出たら既存行を `get` で確認し、同一企業なら新規追加せず `update`（ソースURL・ニーズ要約を追記）。
- 追加後、`<C>/intake/<id>_<slug>.md` の `状態` を `処理済（research 作成）` にする。

### 9. 報告する（短く）
特定結果と確度（1 行）／ ランクとスコア／ 推奨サービス（主→副）／ 冒頭フックに使える観察 1 つ／ 次の一手（`/sales-proposal <id>`）。
懸念（営業 NG 表記、規約上プラットフォーム経由のみ、除外条件該当）があれば先頭に。

## 禁止事項
- プラットフォーム経由の案件について、直接の連絡先（メール・電話・担当者個人）を探して記録すること。目的は提案文を深く書くための理解であり、外部からの直接営業ではない。ユーザーが明示的に求めた場合は、規約上のリスクを 1 行で伝えてから従う。
- ログインが必要な SNS 情報の取得、スクレイピング、推測で埋めた数値。
- `offering.md` にない実績・価格を書くこと。
- 「必ず」「保証」など断定的な表現での課題診断。
