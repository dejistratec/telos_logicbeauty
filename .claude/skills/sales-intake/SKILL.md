# /sales-intake — 取り込み → 企業特定（候補 3 つ）→ 調査 → 提案文 → スプレッドシート

入力: `$ARGUMENTS`（＋添付されたスクリーンショット）

人が行うのは「案件情報を貼る／スクショを添付する」だけ。以降、スプレッドシートに候補と提案文が並ぶところまでをこのスキルで行う。

## クライアントの決め方
- `--client <slug>` → `sales/clients/ACTIVE` の既定 → 登録が 1 つならそれ。複数あって決まらない時だけユーザーに聞く。
- 以降 `<C>` = `sales/clients/<slug>`、`T` = `node sales/scripts/targets.mjs`（既定以外なら `--client <slug>` を付ける）。

## 先に読むもの（毎回）
`sales/README.md` の「守るべきルール」／ `T config`（このクライアントのタブ・独自項目・ステータス・使えるプラットフォーム）／ `<C>/offering.md` ／ `<C>/config.json` ／ `<C>/icp.md` ／ `<C>/outreach.md` ／ `sales/_shared/outreach_rules.md` ／ `sales/_shared/schema.md`

## 手順（案件ごとに繰り返す。複数件まとめて渡されたら 1 件ずつ分ける）

### 0. 共有先から取り込む（チームで使っている場合）
`T share` で共有先を確認し、前回の書き出しがあれば最初に `/sales-list` の「共有先を更新」の手順 1（取り込み）だけを行う。ほかのメンバーが追加した行や付けた id を原本に反映してから、新しい id を取るため。

### 1. 原文を保存し、掲載情報を抜き出す
- **テキスト**: そのまま。**スクリーンショット**: 見えている文字をすべて書き起こす（読めない箇所は `[判読不可]`）。同じ案件の複数枚は 1 件にまとめる。**URL**: WebFetch で本文を取得（ログインが必要で取れなければ、貼り付けかスクショを依頼する）。
- プラットフォームを判定する（サイト名・URL・画面の見た目・文体）。Web 検索や SNS で見つけた企業なら `Web検索` / `SNS`。値は `T config` の「プラットフォーム」から選ぶ（クライアントが追加したサイトもここに出る）。
- `id` を `T next-id` で取り、`sales/_templates/intake.md` の構成で `<C>/intake/<id>_<slug>.md` に保存する（slug は英数字とハイフン。分からなければ業種＋地域。例 `apparel-ec-tokyo`）。
- 掲載情報の表（案件タイトル・依頼内容 200 字以内・予算・納期・依頼条件・掲載企業情報・手がかり）を埋める。**原文に無いことは書かない。**
- 同じ掲載URL が既に登録されていれば（`T list` / 重複エラーで分かる）、新規登録せず既存行を更新する。

### 2. 企業を特定する（プラットフォーム案件のみ。Web検索・SNS は手順 3 へ）
1. 手がかりを列挙する: 固有名詞・商品名・ブランド名／業種／所在地／規模（従業員数・店舗数）／設立年／売上規模／独特な言い回し／URL の断片／発注者名・ニックネーム／評価件数。
2. WebSearch を 5〜8 回。毎回ねらいを変える: 特徴的な語句の完全一致（`"…"`）／業種＋地域＋規模／商品名＋SNS／設立年＋業種＋地域／求人媒体（社名・規模が載りやすい）／業界団体やポータルの一覧。
3. 候補のサイトを WebFetch で開き、**独立した一致点**（事業内容・所在地・規模・設立年・商品・文言・時期）と**矛盾**を数える。
4. 上位 3 社に確度（%）を付ける。高い順、合計 100 以下。残りは「どれでもない」可能性。
   - 独立した一致点 3 つ以上・矛盾なし → 70〜90 ／ 2 つ、または決定的な 1 つ → 40〜65 ／ 1 つ → 15〜35 ／ 業種と地域のみ → 15 未満
   - 候補が 3 社に満たなければ、見つかった分だけでよい。1 社も絞れなければ `企業名` を `（特定不能）業種＋特徴` にする。
5. **掲載者が個人（個人の依頼主・副業）と思われる場合は特定しない。** 対象は事業者だけ。
6. `企業名` は候補1。確度が 50 未満なら `ステータス=調査中`、`次アクション=候補の確認（確度 xx%）`。

### 3. 送付先企業（＝企業名）を調べる（ログイン不要の公開情報のみ）
- 公式サイト: 事業内容・商材・トーン・**問い合わせ先**（フォーム URL / 公開メール / 代表電話）・**営業 NG 表記の有無**。
- クライアントの商材に関係する領域（`offering.md` の「向いている相手」が観察できる場所）。例: SNS 運用なら Instagram / 広告ライブラリ、Web 制作なら現行サイト、採用支援なら採用ページと求人。
- ニュース・プレス・求人で直近 6 か月の「変化」（新店・新商品・資金調達・採用強化・移転）。
- SNS は検索結果に出る範囲（アカウント名・プロフィール・投稿の傾向）だけ。ログインが要る情報、個人の私的アカウントは扱わない。
- 担当者個人の連絡先は探さない。記録するのは会社の公開窓口だけ。
- 候補2・3 は根拠を書ける程度に軽く見る。

### 4. 評価する
- 推奨サービス（主 → 副、`config.json` の id）を `offering.md` §2 の「向いている相手」「組み合わせの定番」から選ぶ。
- `<C>/icp.md` §3 の配点で ICP スコアと内訳を出し、補正を適用してランクを決める。除外条件に当たれば `ランク=除外` `ステータス=除外`、備考に理由。

### 5. 調査メモを書く
`sales/_templates/research.md` の構成で `<C>/research/<id>_<slug>.md`。候補表（確度・一致点・矛盾）、観察、課題仮説、文体の読み取り、スコア内訳を必ず残す。

### 6. 提案文を作る（除外以外は全件、必ず）
`/sales-proposal` の手順 2〜4 をここで実行する（ルールは `sales/_shared/outreach_rules.md`）。
- **提案文_直接**: 企業名の会社に向けて。公開情報だけで書き、掲載情報にしかない内容（予算・締切・募集文の引用・プラットフォーム名）は入れない。メール・フォームなら件名も。
- **提案文_プラットフォーム**: プラットフォーム案件のみ。冒頭 5 行で募集要件に回答。企業名は書かない。
- `<C>/proposals/<id>_<slug>.md` に両方を保存。本文はそれぞれテキストファイル（scratchpad）にも書き出し、手順 7 の JSON から `@file:` で参照する。

### 7. リストに登録する
scratchpad に JSON を書き、`T add <file>`。例:
```json
{
  "プラットフォーム": "ランサーズ", "掲載URL": "https://www.lancers.jp/work/detail/...",
  "案件タイトル": "…", "依頼内容": "…", "予算": "…", "納期・期間": "…", "依頼条件": "…", "掲載企業情報": "…",
  "候補": [
    {"企業名": "株式会社A", "確度": 60, "URL": "https://…", "根拠": "所在地・従業員数・設立年が一致。矛盾なし"},
    {"企業名": "株式会社B", "確度": 20, "URL": "https://…", "根拠": "業種と所在地のみ一致"},
    {"企業名": "C合同会社", "確度": 10, "URL": "https://…", "根拠": "業種のみ一致"}
  ],
  "問い合わせ先": "https://…/contact", "WebサイトURL": "https://…", "SNS": ["ig:@…"],
  "業種": "…", "所在地": "…", "規模": "…", "ニーズ要約": "…", "推奨サービス": ["…"], "属性タグ": ["…"],
  "ICPスコア": 72, "ランク": "B", "接触チャネル": "問い合わせフォーム",
  "件名": "…", "提案文_直接": "@file:/…/T-0001_direct.txt", "提案文_プラットフォーム": "@file:/…/T-0001_platform.txt",
  "ステータス": "提案作成済", "次アクション": "送付", "期限": "YYYY-MM-DD",
  "調査メモ": "sales/clients/<slug>/research/T-0001_xxx.md", "提案文ファイル": "sales/clients/<slug>/proposals/T-0001_xxx.md",
  "原文ファイル": "sales/clients/<slug>/intake/T-0001_xxx.md", "備考": ""
}
```
- 独自項目（`T config` の「独自項目」）: `editable` でない項目は、掲載情報・調査から分かる範囲で埋める（選択肢があればその中から。分からなければ空）。`editable` の項目は人が記入するので空のまま。
- `接触チャネル`: 問い合わせ先がフォーム → `問い合わせフォーム`、メール → `メール`、SNS のみ → `SNS DM`、どれも無ければ `プラットフォーム応募`（プラットフォーム案件）か `未定`。
- `期限`: ランク A は 2 日後、B は 7 日後、C は空。
- 登録結果の行に表示されるタブ名が意図と違う場合（分類の条件に当たる列が空など）は、該当する列を埋めて `T update` する。
- 検証エラーはその場で直して入れ直す（`--force` は使わない）。
- 終わったら intake ファイルの `状態` を `処理済` にする。

### 8. 共有先に反映する
全件の登録が終わったら一度だけ、`/sales-list` の「共有先を更新」（取り込み → 書き出し → 通知）を実行する。更新のタイミングが「取り込みのたび」以外のクライアントでは、書き出さずに「次回の更新でまとめて反映」と報告する。

### 9. 報告する（案件ごとに短く）
- 候補の表（企業名・確度・根拠 1 行）と、送付先に選んだ企業
- ランクとスコア、推奨サービス、作った提案文（直接／プラットフォーム）
- 人の確認が要る点を先頭に: 確度 50% 未満、営業 NG 表記、問い合わせ先が見つからない、除外
- 共有先のリンク（または次回の更新でまとめて反映する旨）

## 禁止事項
- 掲載者が個人と思われる案件で人物を特定すること。担当者個人の連絡先を探すこと。
- ログインが必要な情報の取得、スクレイピング、推測で埋めた数値。
- 確証のない候補を「特定」と書くこと（必ず確度を付ける）。
- 直接連絡用の文面に、掲載情報にしかない内容を入れること。
- `offering.md` にない実績・価格・範囲を書くこと。
